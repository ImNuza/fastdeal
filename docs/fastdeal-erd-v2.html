What changed and why

7 changes: 3 Must 2 Should 2 Nice

Must = a proposal feature breaks or costs more without it. Should = the app runs without it, but a feature looks weaker in the demo. Nice = less work or clearer names only. If you accept only the 3 Must changes, the ERD still works.

1

Price history belongs to the product, not to one wishlist item

Must
OldPrice day links to itemId. Each row belongs to one user's saved item.
NewPrice day links to productKey. One shared history per product. Also stores store.

Why it is better

  • The proposal says Gemini uses "the item's price history" to advise buy now or wait. That verdict shows on the compare page, for any product. In v1, a product that nobody saved has no history, so Gemini has nothing to base "wait" on.
  • Example: Bernard, Zoe and Jayden all save "Sony WH-1000XM5". In v1, the daily check makes 3 SerpApi calls and stores 3 copies of the same prices. In v2, it makes 1 call and stores 1 row per day.
  • The SerpApi free plan gives 250 searches a month. 10 products checked once a day already use 300. Each duplicate call makes this worse.
  • In v1, when a user removes an item, its history is lost or stays behind as orphan rows. In v2, the history stays with the product.
  • store lets the verdict or a chart say where the low price was.

How necessary

Must Without it, the verdict has no history for any product that nobody saved, and the quota runs out sooner. Owners: Ronald (verdict) and Jayden (daily check).

2

One shared productKey on four boxes

Must
OldBoxes match by productName, the exact text the user or SerpApi gave.
NewproductKey on Wishlist item, Sleep hold, Price day and Search log. It is productName in lowercase, trimmed, with single spaces. Product key is drawn dashed because it is a rule, not a collection.

Why it is better

  • "Sony WH-1000XM5" and "sony wh-1000xm5 " are the same product, but Mongo sees two different names.
  • Trending would count them as 2 products. With productKey, it counts 1.
  • The v1 rule "same user cannot save one name twice" lets both spellings in. A unique index on firebaseUid + productKey blocks the second one.
  • Change 1 needs one key that all boxes share. This is that key.

How necessary

Must Change 1 does not work without it. Bernard, Marvel, Zoe and Jayden must all use the same rule, so agree on it once and write it in one place.

3

Wishlist item stores the latest price, store and link

Must
OldOnly savedPrice and targetPrice.
NewAdds latestPrice, latestStore, latestLink and lastCheckedAt.

Why it is better

  • The proposal says the email contains "the new price, the store, and a product link". v1 has nowhere to keep the store and the link, so the email job must call SerpApi again to get them.
  • The wishlist page can show "was $498, now $449 at Lazada" from one read.
  • lastCheckedAt tells the user how fresh the price is. It also tells you if the daily check stopped running.

How necessary

Must The email feature (Jayden) needs these fields to send what the proposal promises.

4

Fixed flag values, and targetPrice can be empty

Should
Oldflag has no fixed values. targetPrice always has a value. The mock sets it to 90% of savedPrice.
Newflag is none, drop or target. targetPrice stays empty until the user sets one. Empty means the 10% rule applies.

Why it is better

  • The proposal says the custom target is used "instead of" the 10% drop. If targetPrice is always 90% of the saved price, "dropped 10%" and "Target reached" happen at the same moment. The two alerts look the same.
  • Fixed values stop one person from writing "dropped" while another person's page checks for "drop".

How necessary

Should The app runs without it, but the demo cannot show two different alerts. Owners: Jayden and Marvel.

5

Sleep hold keeps its start price and a status

Should
OldOnly latestPrice.
NewAdds priceAtStart, status (waiting or done) and productKey.

Why it is better

  • "Still want it?" is more useful as "was $349, now $329". Without priceAtStart, the page can show only one number.
  • With only endsAt, a hold the user already answered shows "Still want it?" every time they open the page. status lets the page hide answered holds.
  • productKey lets the hold read the shared price history from change 1.

How necessary

Should Zoe can finish Sleep On It without these fields, but the result screen is weaker.

6

Session is no longer a collection

Nice
OldSession is a collection with sessionId and startedAt.
NewSession is dashed. The browser makes a random sessionId and keeps it for the visit. Only searchLogs stores it.

Why it is better

  • No feature reads startedAt.
  • "Searched together" groups searchLogs by sessionId. That works without a Session collection.
  • One less model to write, one less write per visit, and one less collection to seed.

How necessary

Nice v1 works. This change only removes work.

7

Keys shown as _id, and collection names on each box

Nice
OldKeys named itemId, holdId, dayId, logId. No collection names. Firebase shows "password".
NewKeys shown as _id. Each box shows its collection name, for example wishlistItems. Firebase shows "password (hashed)".

Why it is better

  • Mongo gives every document an _id automatically. A separate itemId field is a second key that someone must keep in step.
  • The collection name on the box is the third argument to mongoose.model(...), as in the Week 5 blog example. If the code leaves it out, Mongoose makes a second collection called wishlistitems.
  • Users stays keyed by firebaseUid with a unique index. It also gets an automatic _id.
  • "password (hashed)" makes it clear that FastDeal never stores the password.

How necessary

Nice Names only. It prevents confusion when five people write models.

Not changed

  • User: the same 4 fields.
  • Search cache: the same. One optional idea, not drawn: store the Gemini verdict in the same document, so a repeat search does not call Gemini again. That is Ronald's call.
  • Anonymity: searchLogs still has no firebaseUid.
  • Sleep hold needs an account: kept, your call from v1.

Not an ERD change, but it protects the data

  • Express must get firebaseUid from a Firebase ID token that the server verifies. It must not take the uid from the request body. If it does, anyone can read or change any wishlist by sending another uid.
  • Verifying a token needs only the Firebase project ID on the server. The server can read it from VITE_FIREBASE_PROJECT_ID. No service account key is needed, because the server does not create or look up Firebase users. This is Marvel's part.
