Design decisions

10 decisions: 9 Built 1 Dropped

Built = in the code on main on 4 Nov 2026. Dropped = planned, not built, and no longer needed.

1

Product cache: a new collection for the product page

Built
ProblemA search result was the only product data. There was no product page.
DesignproductCache: one row per product, with every store, ratings, reviews, details and a refresh token.

Why it is better

  • One product page costs 1 SerpApi search. The row keeps the result, so opening the product again in the next 24 hours costs nothing.
  • immersiveToken lets the server refresh the store prices after 24 hours without a new search. A failed refresh keeps the old prices and tries again after 1 hour.
  • The row lives 30 days (a TTL index on expiresAt), so a saved product link keeps working.
  • googleLink is the product's Google Shopping page. It has every review, so the product page links there for more than the 3 it shows.

Owner

Dewa (product page, 21 Oct). Ronald's AI verdict can read the same row.

2

Wishlist item is a product, and it lives in MongoDB

Built
ProblemThe wishlist lived in the browser only, and an item was the search the user typed.
DesignOne row per user per product in wishlistItems. productName is the product title. Adds productId, q, image and savedStore.

Why it is better

  • Two products from one search are two rows. Before, saving a second card overwrote the first.
  • The wishlist shows on any computer after login, and the email alerts have data to read.
  • productId and q open the product page again from the wishlist. image shows the product without a new search.
  • An old browser wishlist is copied to MongoDB once at login, then deleted from the browser.
  • Target price fields: targetSource says who set the target (user, ai or empty). targetSuggestion, targetReason and targetSuggestedAt hold the AI hint. The hint never sets an alert.
  • targetEmailFor, targetNotifiedFor and dropNotifiedPrice remember what was already sent. A new email or alert needs a new target or a lower price.

Owner

Marvel (M4, built 21 Oct). Jayden's live price check can use productId.

3

Sleep on it lives on the wishlist item

Built
ProblemHolds were first designed as their own collection, sleepHolds, with a reason and a decision.
DesignThe wishlist item has sleepUntil, sleepPriceAtStart and sleepVerdictSeen. sleepHolds stays in Atlas but the app does not use it.

Why it is better

  • A hold is always on a saved product, and one product has at most one hold. Three fields on the item are enough.
  • The wishlist page reads the hold with the item, so it needs no second query.
  • The reason and decision on sleepHolds are not used. If the team wants them later, they can be two more fields on the item.

Owner

Zoe (Sleep on it) and Jayden (the verdict and the notification).

4

Telegram username is built, for Buy Together

Built
ProblemFriends who want to order together need a way to reach each other.
DesigntelegramUsername is an optional field, stored without "@". The user sets or clears it on the Account page.

Why it is better

  • Buy Together shows friends who saved the same product, with a link to message them on Telegram, so they can order together and split the shipping.
  • It is shown only to accepted friends who saved the same product. Friend search and friend requests never return it.
  • There is no bot. The field is only a contact.

Owner

Marvel (Buy Together, built 21 Oct).

5

Group orders: no collection

Dropped
ProblemAn early idea was a groupOrders collection with invited and joined friends.
DesignNo collection. Buy Together uses one group-order notification and reads the friends live.

Why it is better

  • If the group order is only the smaller Buy Together, notifications are enough. That is what the team built.
  • The friend list is read when the user opens the pop-up, so a friend who removed the product or the friendship is not shown. A stored list would go out of date.
  • The group-order type was already in the notification type list, so no field changed.
6

Search log: one row per browser session per search

Built
ProblemEvery reload wrote a new row, so a few users could push a product to the top of Trending.
DesignA partial unique index on sessionId + productKey for browser sessions. Adds image and count.

Why it is better

  • Trending counts sessions, not reloads.
  • The index covers only browser session ids (they start with "s-"). Seed rows and the old rows with session "1" are not covered, so the seed script still runs.
  • image lets the Trending page show a picture without a new search.

Owner

Bernard (Trending). Index and clean-up by Dewa on 21 Oct: 150 repeat rows deleted, with a backup.

7

Price day: one row per store per day, from the product page

Built
ProblemA row keyed by the search words mixes many products into one row.
DesignOne row per product, per store, per day, keyed by the product title. Written by the product page and by searches. Has productId for reference and source.

Why it is better

  • Search words are not a product: "sony headphones" covers many products. The product title is one product.
  • One row per store keeps each store's price, not only the lowest.
  • source says where a price came from: search (a live search), product (a live product page) or seed (the made-up 30-day history of the demo products). The Home "Comparing pays" card reads only search and product rows.
  • The price history on the product page reads these rows.
8

Search cache keeps the search term and lives 6 hours

Built
ProblemPrices move during the day, so a long cache time shows old prices.
DesignRows live 6 hours. searchTerm is: the clean search term Gemini made from what the user typed.

Why it is better

  • Prices move during the day. 6 hours keeps results fresh and still makes a repeat search free.
  • searchTerm is the page heading on the compare page.
  • Rows with demo set to true are the saved demo searches. The seed keeps them until 31 Jan 2027, so the demo uses no SerpApi credit. productCache has the same demo field.
9

Notification: one Sleep on it alert per countdown

Built
ProblemNothing stopped a second alert for the same countdown.
DesignA partial unique index on firebaseUid + type + productKey for sleep-ended rows, and one on firebaseUid + productKey for sale-soon rows. Adds read.

Why it is better

  • The browser sends the "timer ended" call on every check. The index makes the second call find the first row, so the user gets one alert, and one Buy Together alert.
  • read is the flag the Notifications page uses. readAt is set at the same time. One of the two can go later.
10

Worth it cache: a saved AI verdict, with no links

Built
ProblemEach "Worth it?" verdict costs a Gemini call. A reload would ask again and could give a different answer.
DesignworthItCache: one row per verdict, with key (unique), verdict (an object) and expiresAt (a TTL index).

Why it is better

  • The key is the inputs version, the product id, the price the shopper picked, the cheapest price and the Singapore day. A new price or a new day makes a new key.
  • A reload, and the "How this verdict was made" page, read the same verdict without a new Gemini call.
  • An AI verdict lives 24 hours. An answer from fixed rules, made when Gemini fails, lives 10 minutes, so the page asks Gemini again soon.
  • Nothing links to it, so it does not touch the other collections.

Other notes

  • friendships: Buy Together reads accepted rows only.
  • users: username has a partial unique index. role is user or admin, and the default is user. The admin routes check it. recentSearches holds the user's last 10 searches, newest first. budgetDrafts holds the saved Plan a budget drafts from the Wishlist page, newest first. Each draft has a name, the budget, the ticked items and the combination on screen when it was saved.
  • Product key rule: in models/product-key.js. The client uses the same file for the wishlist routes.

Not an ERD change, but it protects the data

  • Done on 21 Oct: every users, friends, notifications and wishlist route checks the Firebase login token and takes the uid only from it. It needs only the project ID, not a service account key.
  • Friend search and friend requests return usernames, not emails. Username login returns the email only when the password is right.
