FastDeal ERD v4

v4 is the database as it is built now. It adds the product cache, moves the wishlist from the browser to MongoDB, builds the Telegram field for Buy Together and drops the group order collection. Use the switch to see v3. Each new or changed field has a number. Click a number to read why it changed.

The blue line along the top is one line from User to Friendship and Notification. Friendship has two links to User: the user who sends the request and the user who gets it. Sleep hold is faded: the collection is still in Atlas, but the app keeps Sleep on it on the wishlist item now. The lines from Notification to Product key, from Product cache to Wishlist item and from Product cache to Price day are left out so the diagram stays readable. The links table lists them all.

v3 as agreed on 14 Oct 2026, with its change markers. Group order (change 8 in v3) was never built.

What changed since v3 and why

9 changes: 8 Built 1 Dropped

Built = in the code on main and in Atlas on 22 Oct 2026. Dropped = planned in v3, not built, and no longer needed.

1

Product cache: a new collection for the product page

Built
v3No product page. A search result was the only product data.
v4productCache: one row per product, with every store, ratings, reviews, details and a refresh token.

Why it is better

  • One product page costs 1 SerpApi search. The row keeps the result, so opening the product again in the next 24 hours costs nothing.
  • immersiveToken lets the server refresh the store prices after 24 hours without a new search. A failed refresh keeps the old prices and tries again after 1 hour.
  • The row lives 30 days (a TTL index on expiresAt), so a saved product link keeps working.

Owner

Dewa (product page, 21 Oct). Ronald's AI verdict can read the same row.

2

Wishlist item is a product, and it lives in MongoDB

Built
v3The app kept the wishlist in the browser only, and an item was the search the user typed.
v4One row per user per product in wishlistItems. productName is the product title. Adds productId, q, image and savedStore.

Why it is better

  • Two products from one search are two rows. Before, saving a second card overwrote the first.
  • The wishlist shows on any computer after login, and the email alerts have data to read.
  • productId and q open the product page again from the wishlist. image shows the product without a new search.
  • An old browser wishlist is copied to MongoDB once at login, then deleted from the browser.

Owner

Marvel (M4, built 21 Oct). Jayden's live price check can use productId.

3

Sleep on it lives on the wishlist item

Built
v3Holds were planned in sleepHolds, with a reason and a decision.
v4The wishlist item has sleepUntil, sleepPriceAtStart and sleepVerdictSeen. sleepHolds stays in Atlas but the app does not use it.

Why it is better

  • A hold is always on a saved product, and one product has at most one hold. Three fields on the item are enough.
  • The wishlist page reads the hold with the item, so it needs no second query.
  • The reason and decision from v3 were not built. If the team wants them later, they can be two more fields on the item.

Owner

Zoe (Sleep on it) and Jayden (the verdict and the notification).

4

Telegram username is built, for Buy Together

Built
v3telegramUsername was planned for a Telegram bot. Not built.
v4Built as an optional field, stored without "@". The user sets or clears it on the Account page.

Why it is better

  • Buy Together shows friends who saved the same product, with a link to message them on Telegram, so they can order together and split the shipping.
  • It is shown only to accepted friends who saved the same product. Friend search and friend requests never return it.
  • There is no bot. The field is only a contact.

Owner

Marvel (Buy Together, built 21 Oct).

5

Group orders: no collection

Dropped
v3groupOrders with invited and joined friends. Planned, not built.
v4No collection. Buy Together uses one group-order notification and reads the friends live.

Why it is better

  • v3 already said: if the group order becomes the smaller Buy Together, notifications are enough. That is what the team built.
  • The friend list is read when the user opens the pop-up, so a friend who removed the product or the friendship is not shown. A stored list would go out of date.
  • The group-order type was already in the notification type list, so no field changed.
6

Search log: one row per browser session per search

Built
v3Every reload wrote a new row, so a few users could push a product to the top of Trending.
v4A partial unique index on sessionId + productKey for browser sessions. Adds image and count.

Why it is better

  • Trending counts sessions, not reloads.
  • The index covers only browser session ids (they start with "s-"). Seed rows and the old rows with session "1" are not covered, so the seed script still runs.
  • image lets the Trending page show a picture without a new search.

Owner

Bernard (Trending). Index and clean-up by Dewa on 21 Oct: 150 repeat rows deleted, with a backup.

7

Price day: one row per store per day, from the product page

Built
v3One row per product per day, written from the search, keyed by the search words.
v4One row per product, per store, per day. Written by the product page, keyed by the product title. Adds productId for reference.

Why it is better

  • Search words are not a product: "sony headphones" covers many products. The product title is one product.
  • One row per store keeps each store's price, not only the lowest.
  • No page reads these rows yet. Showing the history is Dewa's task D5.
8

Search cache keeps the search term and lives 6 hours

Built
v3Rows lived 24 hours.
v4Rows live 6 hours. Adds searchTerm: the clean search term Gemini made from what the user typed.

Why it is better

  • Prices move during the day. 6 hours keeps results fresh and still makes a repeat search free.
  • searchTerm is the page heading on the compare page.
9

Notification: one Sleep on it alert per countdown

Built
v3No rule against a second alert for the same countdown.
v4A partial unique index on firebaseUid + type + productKey for sleep-ended rows. Adds read.

Why it is better

  • The browser sends the "timer ended" call on every check. The index makes the second call find the first row, so the user gets one alert, and one Buy Together alert.
  • read is the flag the Notifications page uses. readAt is set at the same time. One of the two can go later.

Not changed

  • friendships: the same. Buy Together reads accepted rows only.
  • users: username and its partial unique index are the same. recentSearches is in the schema, but only the seed writes it so far.
  • Product key rule: the same, in models/product-key.js. The client uses the same file for the wishlist routes.
  • Every v3 field stays. Nothing is renamed or removed.

Not an ERD change, but it protects the data

  • Done on 21 Oct: every users, friends, notifications and wishlist route checks the Firebase login token and takes the uid only from it. It needs only the project ID, not a service account key.
  • Friend search and friend requests return usernames, not emails. Username login returns the email only when the password is right.
