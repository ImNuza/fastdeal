What changed and why

9 changes: 6 Must 2 Should 1 Nice

Must = a job on the 13 Oct board cannot be built without it. Should = needed for a feature that is not settled yet. Nice = only for an extra. The owner and task id refer to the 13 Oct to-do page.

1

User gets a unique username

Must
OldA user has only email. The tape at 52:47 says "right now, the username is the email".
Newusername: lowercase, 3 to 20 letters, digits, dots or underscores. Unique. Empty until the user picks one.

Why it is better

  • Friends add each other by username (tape 49:47). Searching friends by email shows a stranger's email address, so a username is safer.
  • The unique index uses a partial filter: it checks only users who have a username. Old users with no username do not clash. A plain unique index would fail on the second empty value.

How necessary

Must Friends (t-19) needs it. Owner: Marvel (t-18).

2

Friends get their own collection, not a list inside User

Must
Boardfriends: [] inside the user box. Not in v2.
Newfriendships: one row per pair, with requesterUid, addresseeUid, status and a unique pairKey.

Why it is better

  • A friend request has a state. It starts as pending and becomes accepted or blocked (tape 35:23: add, remove, block). A plain list of uids cannot store "pending".
  • With a list in each user, adding a friend means two writes: Zoe's list and Marvel's list. If one write fails, Zoe sees Marvel but Marvel does not see Zoe. One row per pair cannot get out of step.
  • pairKey is the two uids in sorted order, for example uidA|uidB. Its unique index stops a second request when the other person already asked.
  • Remove = delete the row. Block = set status to blocked and blockedByUid to the user who blocked. The blocked user cannot ask again, and only the user who blocked can unblock.

How necessary

Must The friends list (t-19) and the group order (t-17) need it. Owner: Marvel.

3

Notifications get their own collection

Must
Boardnotif: [] inside the user box. Not in v2.
Newnotifications: one row per alert, with type, title, body, link, readAt and emailedAt.

Why it is better

  • A notification list grows with no limit. Each new alert would rewrite the whole user document, and every page that reads the user would load every old alert too.
  • One collection serves every sender: price drop and target (Jayden), Sleep on it ended (Jayden), group order (Jayden), friend request (Marvel), sale soon (Dewa). Bernard's page reads one place.
  • type has fixed values: price-drop, target-hit, sleep-ended, group-order, friend-request, friend-accepted, sale-soon. Same reason as the v2 flag values: one spelling for everyone.
  • readAt empty = unread. The navbar count is "rows for this user where readAt is empty". emailedAt shows if an email also went out, so the email job does not send twice.
  • link is the page to open, for example /sleep. The Notifications page does not need to know each type.

How necessary

Must The Notifications page (t-9) shows nothing without it. Owner: Bernard. Writers: Jayden, Marvel, Dewa.

4

Sleep hold keeps the reason and the answer

Must
OldFixed 24-hour hold. status is waiting or done.
NewThe user picks endsAt. Adds reason, reasonNote and decision. status adds ended.

Why it is better

  • Jayden's verdict answers the user's own reason: "you waited for a better price, and it dropped 15%" (feature tape 01:37). The reason must be saved to do that.
  • reason has fixed values: better-price, wait-for-sale, not-sure-i-need-it, other. reasonNote is optional free text.
  • ended means the timer is over and the notification went out, but the user has not answered yet. The timer job looks for waiting holds past endsAt, so it never alerts twice.
  • decision (buy or skip) lets the app count how often Sleep on it stops a purchase. That is a good number for the final talk.
  • No duration field. The duration is endsAt minus startedAt.

How necessary

Must Smart Sleep on it (t-16) needs the reason and the ended state. Owner: Jayden.

5

Wishlist item gets a priority rank

Must
OldNo way to mark an item as important.
Newpriority: a number, 1 = most important. Empty = no priority.

Why it is better

  • The board says the user "highlights which of their products are of priority". The tape at 39:14 says "one is the most important". A rank number stores both facts: if it is a priority, and its order.
  • The best-combination feature (t-15) reads the rank to pick items first when the budget is small.
  • The budget itself is not stored. It is a slider on the page (tape 41:30).

How necessary

Must Priority tags (t-14) and the best combination (t-15) need it. Owner: Zoe.

6

Price day keeps the "was" price

Must
OldPrice day stores price and store only.
NewAdds oldPrice: the crossed-out price the store showed that day. Empty when there is none.

Why it is better

  • SerpApi gives this value as extracted_old_price on some listings. Our sample file has one: price $132.72, "Usually $116".
  • A gimmick is a "was" price that shows on most days for months (feature tape 02:20). To see "most days", each day's old price must be saved. Today's search alone cannot show it.
  • The check: if oldPrice shows on most days and price never reached it, the label is "Probably a gimmick". If the price really was at oldPrice recently, the label is "Real discount". With less than about 30 days of rows, the label is "Not enough history yet". The team sets the exact numbers.

How necessary

Must The discount check (t-2) has no evidence without it. Owner: Dewa.

7

User keeps the last 10 searches

Should
BoardA second box with user: str and hist: []. Not in v2.
NewrecentSearches inside the user: a list of { query, productKey, searchedAt }, never more than 10.

Why it is better

  • The tape at 54:35 to 54:45 sets a limit of ten, newest on top. A list with a fixed limit is safe to keep inside the user. Mongo can add the new search and cut the list to 10 in one write.
  • Compare change 3. Notifications have no limit, so they get their own collection. Recent searches have a limit, so they stay inside the user.
  • searchLogs stays anonymous. Tape 54:23: "it's anonymous. You don't put it here." This list is only for the user's own page and is never shown to others.

How necessary

Should Recent searches (t-7) is a later task. Owner: Ronald.

8

Group orders get their own collection

Should
OldNo group order in v2. The board steps 1 to 4 describe one.
NewgroupOrders: who started it, the product and deal, who was invited, who joined, and open or closed.

Why it is better

  • Board step 4: the user starts a group order and the chosen friends get an alert. The app must remember who was invited and who said yes. That state belongs to the order, not to any one user.
  • The invited and joined lists are inside the row because a group order has only a few friends. That is the same rule as change 7.
  • Price, store and link are copied in, so all friends see the same deal even if the price changes later.

How necessary

Should Only if the team keeps the group order as drawn. If it becomes the smaller "Buy together" from the 13 Oct meeting notes (send friends the deal link), the notifications from change 3 are enough and this collection is not needed. Owner: Jayden (t-17).

Not changed

  • searchLogs: the same. Bernard's trending counts by productKey. The "similar products" idea from the prof can group by sessionId. Both work with the v2 indexes.
  • searchCache: the same schema. listings is a plain list, so Ronald's filter can mark each listing as product or accessory inside it. The "Goes well with" section can then read the accessories from the same cache row, with no extra SerpApi call.
  • Product key rule: the same. Notifications and group orders use it too.
  • Every v2 field stays. Nothing is renamed or removed, so the current user routes and the seed keep working.

Not an ERD change, but it protects the data

  • On main, GET /api/users/:uid and PUT /api/users/:uid take the uid from the URL. Anyone who knows a uid can read or change that user.
  • v3 makes this worse if it stays: friends and notifications hold more personal data. The server must take the uid from a verified Firebase ID token. This is Marvel's task t-20, and it only needs the project ID.
